# Research: 007-firestore-data

Документація rnfirebase.io під час планування не відповідала, тому API звірено за типами пакета `@react-native-firebase/firestore@27.1.1` (`dist/typescript/lib/modular`, `types/firestore.d.ts`, `RNFBFirestore.podspec`). Поведінку нативних SDK Firestore (черга записів, кеш) взято з документації Firebase; її перевіряє quickstart.

## R1. Бібліотека й API

- **Decision**: `@react-native-firebase/firestore` 27.1.1 (та сама версія, що й `app`/`auth`), модульний API: `getFirestore`, `collection`, `doc`, `onSnapshot`, `setDoc`, `deleteDoc`, `writeBatch`, `getDocFromServer`, `getDocsFromServer`, `waitForPendingWrites`, `initializeFirestore`/`cacheSizeBytes`. Усі ці імена є в 27.1.1.
- **Rationale**: нативні SDK Firestore дають справжній офлайн-кеш і чергу записів на iOS і Android; RN Firebase уже в проєкті, той самий Firebase-проєкт і SPM-збірка. Модуля Expo для Firestore немає (принцип I: стороння бібліотека виправдана).
- **Alternatives**: Firebase JS SDK (`firebase/firestore`) — на RN без IndexedDB немає постійного кешу, офлайн після перезапуску не працює; власний бекенд — надлишково.

## R2. Нативна збірка

- **Decision**: `npx expo install @react-native-firebase/firestore`; окремого config plugin немає (пакет не має `app.plugin.js`, підключення робить плагін `@react-native-firebase/app`). Потрібна нова development build; `ios/` і `android/` перегенеровуються `npx expo prebuild --clean` і комітяться, як у 006.
- **Rationale**: podspec тягне SPM-продукт `FirebaseFirestore` через `firebase_spm` — так само, як Auth.
- **Ризик**: precompiled modules Expo SDK 58 уже губили спільні SPM-продукти (`plugins/with-google-signin-spm-link.js`). Якщо iOS-лінкування впаде з `Undefined symbol` — додати відсутній продукт у цей плагін. FirebaseFirestore (gRPC, abseil, leveldb) помітно подовжує першу iOS-збірку.

## R3. Офлайн і «локальна копія» (FR-005, FR-008, FR-017)

- **Decision**: локальна копія даних акаунта — постійний кеш Firestore (на iOS/Android увімкнений за замовчуванням), окремого дзеркала в AsyncStorage немає. Розмір кешу — стандартний (100 МБ), він на порядки більший за дані користувача.
- **Rationale**: кеш Firestore спільний для застосунку, але документи лежать за шляхами `users/{uid}/…`, а слухачі підписуються лише на шлях поточного користувача, тож дані іншого акаунта не показуються (FR-008). Черга незбережених записів у нативних SDK ведеться **окремо для кожного користувача**: при зміні користувача SDK перемикається на його чергу, а черга попереднього лишається на диску й відправляється, коли той знову увійде (саме це вимагає FR-017). Після виходу кеш не чиститься (`clearPersistence` не викликається) — повторний вхід показує дані одразу.
- **Alternatives**: дзеркало стану в AsyncStorage з власною чергою синхронізації — дублює те, що SDK уже робить, і складно з конфліктами.

## R4. Записи без очікування сервера (FR-004)

- **Decision**: методи репозиторіїв застосовують запис і повертаються, не чекаючи підтвердження сервера: проміс `commit()`/`setDoc()` не `await`-иться (помилка — лише в лог dev-збірки). Знімок оновлює слухач `onSnapshot`, який одразу отримує локальну зміну (`hasPendingWrites`).
- **Rationale**: проміс запису Firestore завершується лише після підтвердження сервера; без інтернету він висить, і `await repository.addObject()` на екрані завис би. Ідентифікатори нових обʼєктів і послуг генеруються локально (`doc(collection(...)).id`), тож `addObject` повертає обʼєкт одразу.
- **Синхронне оновлення знімка**: щоб екрани, які читають знімок одразу після мутації (`await addObject` → перехід на екран обʼєкта), бачили зміну, репозиторій також застосовує зміну оптимістично — до масиву тієї колекції, з якої збирається знімок (а не лише до зібраного знімка, інакше знімок іншої колекції перезбере стан зі старого масиву й зміна мигне); наступний `onSnapshot` цієї колекції замінює масив станом із кешу.

## R5. Перше завантаження й «немає інтернету» (FR-011)

- **Decision**: стан даних акаунта — `loading | offline | ready`. Прапорець `accountDataSynced:{uid}` у `KeyValueStorage` означає, що цей пристрій уже хоч раз отримав дані акаунта з сервера.
  - Прапорець є → слухачі з кешу дають дані за мілісекунди, стан одразу `ready` (провайдер, як зараз, рендерить `null` до першого знімка з кешу). Скелетонів немає.
  - Прапорця немає → стан `loading` (скелетони), запускається `getDocFromServer(users/{uid})` + `getDocsFromServer` колекцій. Успіх → прапорець, міграція (R7), стан `ready`. Помилка `firestore/unavailable` → `offline` (повідомлення з «Спробувати ще», яке повторює серверне читання).
- **Інші помилки серверного читання** (`permission-denied`, коли правила не опубліковані) теж дають `offline`, але код пишеться в лог dev-збірки (`[firestore] <код>`); quickstart підказує перевірити правила, якщо «Немає інтернету» видно з мережею.
- **Rationale**: слухач `onSnapshot` без мережі не дає помилки, лише `fromCache: true`, — відрізнити «немає даних» від «ще не завантажено» він не може. Серверне читання без мережі відхиляється (`unavailable`), а з мережею й наповнює кеш.
- **Alternatives**: таймаут над `fromCache` — довільна затримка і хибні «немає інтернету»; `@react-native-community/netinfo` — нова залежність, а «мережа є» ще не означає «Firestore доступний».

## R6. Видалення акаунта (FR-009)

- **Decision**: `AuthService.deleteAccount(deleteData)` отримує колбек видалення даних і викликає його після повторного підтвердження Apple (якщо потрібне) і перед відкликанням доступу Apple (iOS) та `deleteUser`: порядок — перепідтвердження Apple → `deleteData` → `revokeToken` → `deleteUser`, щоб невдале видалення даних не лишало акаунт з відкликаним доступом до Apple ID. `deleteData` = серверне читання `users/{uid}` (без мережі → `unavailable` → `AuthError('failed')`, нічого не видалено) → видалення всіх документів акаунта батчами по ≤ 500 операцій з очікуванням `commit()` і таймаутом 20 с → видалення прапорця `accountDataSynced:{uid}`. Для Google `deleteUser` після видалення даних може вимагати `requires-recent-login`; повторний вибір акаунта, як зараз.
- **Rationale**: правила безпеки пускають лише автентифікованого власника, тож дані треба видаляти до видалення акаунта. Видалення документів застосовується й до локального кешу — копії на пристрої не лишається. Серверних функцій немає (тариф Spark).
- **Відомий компроміс**: якщо дані видалено, а `deleteUser` потім не вдався (скасоване перепідтвердження Google), акаунт лишається порожнім; повторне видалення його добиває. Це прийнятно, бо користувач уже підтвердив намір видалити все.

## R7. Перенесення даних попередньої версії (FR-010)

- **Decision**: після першого успішного серверного читання (R5) для акаунта: якщо в AsyncStorage є ключ `ledgerState` (або `outageSettings` з містом/чергами), а в акаунті немає ні обʼєктів, ні документа налаштувань «Світла» — усе записується в Firestore батчами з тими самими ідентифікаторами (`commit()` без очікування — потрапляє в чергу й працює офлайн). Після цього (і також якщо акаунт уже має дані) ключ `ledgerState` і місто/черги в `outageSettings` видаляються з AsyncStorage — вдруге й в інший акаунт вони не перенесуться. Профіль переноситься наявним правилом `syncFromAuth` (імʼя з `userProfile`, змінене користувачем), після чого ключ `userProfile` видаляється.
- **Rationale**: «акаунт порожній» визначається лише після серверного читання, інакше порожній кеш нового пристрою дав би хибне «порожньо» й затер би дані акаунта.

## R8. Розкладка й ідентифікатори

- **Decision**: `users/{uid}` (профіль), `users/{uid}/objects/{objectId}`, `services/{serviceId}`, `readings/{serviceId}_{month}`, `months/{objectId}_{month}`, `dayCounts/{serviceId}_{month}`, `amounts/{serviceId}_{month}`, `settings/outages` (місто й черги). Деталі — [data-model.md](data-model.md).
- **Rationale**: природні ключі роблять повторний запис за той самий місяць заміною (FR-002, edge case «показник двічі»); окремі колекції — дрібні документи й дешеві оновлення. Місяці в ідентифікаторі (`2026-11`) не містять `/`.

## R9. Каскадні видалення й конфлікти

- **Decision**: `deleteObject`, `deleteService`, `deleteMonth`, `moveMonth`, `resetEntry` будують список операцій з поточного знімка й застосовують їх батчами (≤ 500 операцій, кілька батчів для великих обʼєктів). Знімок, який віддає репозиторій, відкидає «сиріт» (послуги без обʼєкта, показники/дні/суми без послуги, місяці без обʼєкта), щоб одночасні зміни з двох пристроїв не ламали екрани. Конфлікти — «пізніший запис перемагає» (стандарт Firestore).
- **Alternatives**: транзакції — не працюють офлайн.

## R10. Правила безпеки

- **Decision**: `firestore.rules` у корені репозиторію (+ `firebase.json` з посиланням на нього) з правилом «лише власник `users/{uid}/**`»; публікує користувач у консолі або `firebase deploy --only firestore:rules`. Базу (Standard, `europe-central2`, production mode) створює користувач у консолі.
- **Rationale**: FR-003/SC-007; правила під контролем версій.

## R11. Web

- **Decision**: на web лишаються локальні репозиторії (`index.web.ts`), як заглушка входу з 006; `src/services/account-data/index.web.ts` — заглушка без Firestore (статус завжди `ready`, `deleteAccountData` нічого не робить), щоб web-бандл не тягнув нативний модуль; web поза обсягом.

## R12. Скелетони

- **Decision**: блок зі скелетона «Світла» (`Bone` у `src/views/outages/outage-skeleton.tsx`) виноситься в спільний `src/components/skeleton.tsx` (`SkeletonBone`, спільний прогрес відблиску); скелетони вкладок — у `src/views/account-data/`. Нові артборди канвасу: «05s · Обʼєкти — завантаження», «20d · Світло — завантаження даних акаунта», «14s · Аналітика — завантаження», «16s · Профіль — завантаження», «05o · Немає інтернету — дані не завантажено».
